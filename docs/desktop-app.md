# The desktop app

The desktop app is the same React UI as the web app, in a Tauri 2 window, with a small native side in Rust (`src-tauri/`). The native side signs in through the system browser and keeps refresh tokens out of the UI, makes network requests (so CORS doesn't apply), talks IMAP and SMTP for "other mail server" accounts, and integrates with the desktop: tray, autostart, `mailto:` links, notifications, the unread badge and updates. This document describes that native side, the IPC between it and the UI, and the `Platform` interface that keeps the rest of the UI unaware of it. User-facing features and the OAuth registrations are in the [README](../README.md#desktop-app); how the two shells fit into the whole in [architecture.md](architecture.md); builds in [building-and-deploying.md](building-and-deploying.md); releases in [releasing.md](releasing.md).

## Overview

```
┌──────────────── web view (dist/) ────────────────┐      ┌──────── native side (Rust) ────────┐
│ React UI ── Platform (src/platform/native) ─────┼─IPC─▶│ shell.rs   tray, window, mailto    │
│          ── NativeAuthSession (src/auth/native) ─┼─IPC─▶│ oauth/     sign-in, tokens ── vault│──▶ OS keychain
│ providers ── fetch = nativeFetch ────────────────┼─IPC─▶│ net.rs     HTTP (reqwest)          │──▶ Gmail, Graph, iCal…
│ AI assistant ── backend (native/ai.ts) ──────────┼─IPC─▶│ ai/        keys, streaming ── vault│──▶ Claude, OpenAI, …
│ IMAP provider ── bridge (native/imap.ts) ────────┼─IPC─▶│ imap/      IMAP, SMTP ── vault     │──▶ mail servers
└──────────────────────────────────────────────────┘      └────────────────────────────────────┘
```

- `src/main.tsx` detects the app (`"__TAURI_INTERNALS__" in window`) and only then loads `src/platform/native` with `import()`, so the web bundle never runs it. `startDesktop()` returns the desktop `Platform`, a native `fetch`, the sign-in bridge and the accounts kept from earlier starts; the composition root (`src/app/services.ts`) passes them to the Gmail and Microsoft modules and to iCal subscriptions.
- The window (`app.windows` in `src-tauri/tauri.conf.json`) is labelled `main`, starts invisible (`visible: false`; the native side shows it unless started hidden), has a minimum size of 360 × 480, uses `https://tauri.localhost` on Windows (`useHttpsScheme`), and leaves file drops to the web view (`dragDropEnabled: false`), so dropping files on the composer works as in the browser.
- `withGlobalTauri` is off: the UI talks to Tauri only through the `@tauri-apps/*` packages, imported in `src/platform/native` alone.

`auth_*` failures reach the UI as `{ kind, message }` (`AuthError` in `oauth/mod.rs`, serialized with `tag = "kind"`). `toNativeError()` in `authBridge.ts` turns them into a `NativeAuthError`, and `nativeAuthError()` in `NativeAuthSession.ts` into the `MailError` the UI already handles:

| `kind`         | Meaning                                                  | `MailError` kind and reason                                                       |
| -------------- | -------------------------------------------------------- | --------------------------------------------------------------------------------- |
| `reauth`       | The refresh token is gone or refused                     | `auth-required`, `signInAgain`; the session becomes `expired` (the Reconnect bar) |
| `scopes`       | The account hasn't granted the scopes asked for          | `unavailable`, `calendarAccessNeeded`: only that feature is unavailable           |
| `cancelled`    | Another sign-in started, or the 10 minutes ran out       | `auth-required`, `signInClosed`                                                   |
| `denied`       | The user declined, or required scopes weren't granted    | `auth-required`, `accessNotGranted`                                               |
| `wrongAccount` | Signed in with another account than the one reconnecting | `auth-required`, `wrongAccount` (with both addresses)                             |
| `network`      | No answer from the provider                              | `network`, `unreachable`                                                          |
| `provider`     | Any other refusal                                        | `provider`, `signInFailed` (with the provider's text)                             |

`imap_*` failures reach the UI as `{kind, message, server?, certificate?}` (`MailServerError` in `imap/error.rs`, the same shape and kinds as in `src/accounts/mailServer.ts`); `src/platform/native/imap.ts` turns them into its `MailServerError`. See [IMAP and SMTP](#imap-and-smtp).

| Event                 | When                                                              | Listener                                                                  |
| --------------------- | ----------------------------------------------------------------- | ------------------------------------------------------------------------- |
| `a0://poll`           | Every 5 minutes while the window is hidden                        | `platform.onPollRequest` ← `useMailSync()` (`src/ui/sync/useMailSync.ts`) |
| `a0://compose`        | A `mailto:` link or the tray's **New mail** (empty link)          | `platform.onCompose` ← `DesktopIntegration` → `composeFrom()`             |

## Capabilities and CSP

`src-tauri/capabilities/desktop.json` grants the `main` window exactly what the UI calls on the desktop (`android.json` is the Android app's, see [android.md](android.md)):

| Permission                                            | For                                                                                                                                                           |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `core:default`                                        | Tauri's core defaults (events, window and app basics)                                                                                                         |
| `core:window:allow-show`, `-set-focus`, `-unminimize` | Bringing the window forward on notification clicks (hiding it into the tray happens on the native side)                                                       |
| `opener:default`                                      | `openUrl` for `http(s):`, `mailto:` and `tel:` (the plugin's default scope, which also allows revealing a file in its folder); no opening of paths            |
| `dialog:allow-save`                                   | The Save dialog for attachments                                                                                                                               |
| `fs:allow-write-file`                                 | Writing the attachment. There's no fs scope, so only paths the user just picked in the Save dialog (which the dialog plugin adds to the scope) can be written |
| `notification:default`                                | Permission, sending, click actions                                                                                                                            |
| `autostart:default`                                   | Enable, disable, query                                                                                                                                        |
| `updater:default`                                     | Check, download, install                                                                                                                                      |
| `process:allow-restart`                               | Relaunch after an update                                                                                                                                      |

The app's own commands (`net_*`, `auth_*`, `shell_*`) need no entry here: `src-tauri/build.rs` defines no app manifest, and Tauri then allows registered commands to the app's own pages (never to remote ones). Opening downloaded files with another app isn't a plugin permission at all: `shell_open_file` writes them on the native side into its own folder and opens that path.

The app's CSP is `app.security.csp` in `src-tauri/tauri.conf.json` (the Vite meta CSP is skipped for desktop builds):

```
default-src 'self'; script-src 'self'; connect-src ipc: http://ipc.localhost;
img-src 'self' data: blob: https: http:; style-src 'self' 'unsafe-inline';
font-src 'self' data:; frame-src 'self' blob:; media-src 'self' blob:;
object-src 'none'; base-uri 'none'; form-action 'none'
```

- `connect-src` allows only Tauri's IPC: the UI's own `fetch` can't reach the network, so every request goes through `net_fetch`.
- `script-src 'self'`: no Google or Microsoft scripts; sign-in is native.
- `img-src https: http:` is there for remote images in mail once the user allows them; the mail iframe's own CSP blocks them until then ([security.md](security.md#html-mail)).
- `dangerousDisableAssetCspModification: ["style-src"]` stops Tauri from adding nonces/hashes to `style-src`; with a nonce present, browsers ignore `'unsafe-inline'`, which mail HTML needs (it's rendered in `srcdoc` frames, which inherit the app's CSP).
- `freezePrototype: true` freezes `Object.prototype` in the web view against prototype pollution.
- `devCsp` is `null`, i.e. not set. Tauri injects the CSP into the bundled `dist/`; under `npm run app:dev` the window loads the Vite dev server instead, so development runs without the app CSP (like `npm run dev` in the browser).

## Native sign-in

Google blocks sign-in inside embedded web views, so the desktop app signs in with the system browser (OAuth authorization code flow with PKCE and a loopback redirect, RFC 8252 style). The flow, in `oauth/mod.rs` `browser_sign_in()`:

1. A new sign-in cancels one still waiting (only one at a time).
2. `Loopback::bind()` listens on `127.0.0.1` at a random free port, and on `::1` at the same port if it can (for browsers that resolve `localhost` to IPv6).
3. A PKCE pair (32 random bytes → 43-character verifier, S256 challenge) and a random `state` are made.
4. The authorize URL opens in the default browser (`tauri-plugin-opener`):

   |                 | Google                                      | Microsoft                                                                           |
   | --------------- | ------------------------------------------- | ----------------------------------------------------------------------------------- |
   | Authorize       | `accounts.google.com/o/oauth2/v2/auth`      | `login.microsoftonline.com/common/oauth2/v2.0/authorize`                            |
   | Redirect URI    | `http://127.0.0.1:<port>/`                  | `http://localhost:<port>/desktop` (Entra ignores the port)                          |
   | Extra parameter | `access_type=offline` (for a refresh token) | `response_mode=query`                                                               |
   | Client          | "Desktop app" client ID **and secret**      | The same Entra client ID as the web app, "Mobile and desktop applications" platform |

   Both get `response_type=code`, the scopes, `state`, the challenge, `prompt` (`select_account`, or `consent` when asking for more) and `login_hint` for a known account.

5. The loopback server waits up to 10 minutes. It takes only a `GET` to the redirect path that carries a `state`; anything else (a favicon request) gets a 404. It answers with a minimal page, no scripts, `Cache-Control: no-store`, showing one of two texts the UI sent with the request (`PageTexts`): done or failed. The UI picks them from `desktop.signedIn` in `src/i18n/texts/desktop.ts`, in the interface's language (`signedInPage` in `src/main.tsx`), and they're HTML-escaped.
6. `state` must match; `error=access_denied` becomes `denied`, other errors `provider`.
7. The code is redeemed **in Rust** (`code_form()`): with the verifier and redirect URI, plus the client secret for Google and the scopes again for Microsoft. The module docs give the reasons: Microsoft refuses the exchange from a web view, and refresh tokens must never reach the UI.
8. The granted scopes (from the token response, or the requested ones if it doesn't say) must include the request's `required` scopes, or the sign-in fails as `denied`.
9. The address comes from the ID token (`email`, else `preferred_username`; for Microsoft also the tenant `tid`). It's read without checking the signature, because it came straight from the token endpoint over TLS. The account key is `gmail:<address>` or `microsoft:<address>` in lower case, the same id the UI uses.
10. If the provider sent no new refresh token (a repeated sign-in), the stored one is kept. The account goes into the vault, the access token into memory.

**Wrong account.** `auth_sign_in` (reconnecting a known account) compares the key of whoever signed in with the expected one and fails with `wrongAccount` if they differ; nothing about the other account is kept. `auth_connect` (a new account) takes whoever signs in.

**Access tokens.** `auth_token` checks that the account's granted scopes cover the request (else `scopes`), returns the cached token while it has more than 2 minutes left, and otherwise renews it with the refresh token. Renewals run one at a time behind a mutex, because Microsoft hands out a new refresh token with each renewal (which replaces the stored one). `invalid_grant`, `interaction_required` or `consent_required` from the token endpoint mean `reauth`.

**Sign-out.** `auth_sign_out` drops the access token and the vault entry, then revokes the refresh token at `oauth2.googleapis.com/revoke` (best effort). Microsoft has no revocation endpoint for public clients, so its token is only forgotten.

**On the TS side**, `NativeAuthSession` (`src/auth/native/NativeAuthSession.ts`) implements the same `AuthSession` as the web sessions, but with `expiresAt` undefined: renewal is silent, so nothing waits for a click. Concurrent sign-ins share one browser window. The modules build the requests:

| Module                                          | Scopes asked for (`NATIVE_SCOPES`)                                                                                                                                                     | Required                      |
| ----------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------- |
| Gmail (`src/providers/gmail/module.ts`)         | `https://mail.google.com/`, contacts (2), `gmail.settings.basic`, calendar (2), `openid`, `email`: everything at once, as the code notes desktop apps can't add scopes later at Google | `https://mail.google.com/`    |
| Microsoft (`src/providers/microsoft/module.ts`) | `GRAPH_SCOPES`, `Calendars.ReadWrite`, `openid`, `profile`                                                                                                                             | `Mail.ReadWrite`, `Mail.Send` |

Why each scope is needed is in [security.md](security.md#scopes-per-provider). Registering the two clients is in the README ([Signing in from the desktop app](../README.md#signing-in-from-the-desktop-app)).

## Vault and keychain

`src-tauri/src/vault.rs` keeps, per account key: provider, client (ID, and the secret for Google), refresh token, granted scopes, address and Microsoft tenant. The same code keeps the AI assistant's keys and sign-ins in a second file, `ai.vault` (see [AI assistant](#ai-assistant)), and IMAP accounts' settings and passwords or Yahoo/AOL refresh tokens in a third, `imap.vault` (see [IMAP and SMTP](#imap-and-smtp)); `Vault<T>` is generic over what a file holds.

- **Encryption:** XChaCha20-Poly1305 with a 256-bit key and a new random 24-byte nonce on every write. File layout: `A0V1` magic, nonce, ciphertext of the JSON.
- **Key:** 32 random bytes in the OS keychain through the `keyring` crate (Secret Service over D-Bus on Linux, the Keychain on macOS, Credential Manager on Windows), under the service name `app.action0.mail` (the app identifier) and the entry `vault-key`. Only the key goes there, because keychains limit entry sizes (Windows: 2560 bytes) and refresh tokens can be longer. All files use this one key: `SharedKey` loads it (or makes and saves it) once, on first use, so the files can never end up with different keys.
- **File:** `accounts.vault` in the app's data folder (`app_data_dir()`, named after the identifier: `~/.local/share/app.action0.mail/` on Linux, `~/Library/Application Support/app.action0.mail/` on macOS, `%APPDATA%\app.action0.mail\` on Windows). Writes go to a sibling `.tmp` file that is renamed over it, so a crash never leaves half a file; on Unix the file is `0600`.
- **Unreadable file or other key:** the vault starts empty (the accounts need signing in again).
- **No keychain:** if the keychain can't be read or written, the vault has no key and writes nothing. Accounts work, but only until the app quits; `auth_accounts` reports `persistent: false`, which the platform passes on as `DesktopControls.keychain`. Settings → App then says so (with the Linux hint), and the toast after connecting an account reads "Connected … (until you quit)".

Access tokens are never stored: they live in the `Auth` state's memory and are handed to the UI per request.

## Networking

In the app, every provider request goes through the native side: the Gmail, Microsoft and iCal providers get `desktop.fetch` instead of the browser's `fetch` (`src/main.tsx`, `src/app/services.ts`). That's why iCal addresses load from any server in the app, while the web app depends on CORS headers ([README](../README.md#calendars-by-address-ical)); CalDAV requests have their own command (`caldav_request`), which adds the server's login.

`createNativeFetch()` (`src/platform/native/nativeFetch.ts`) is a drop-in `fetch`:

1. It normalizes the input with `new Request(…)` and reads the body as bytes.
2. It calls `net_fetch` with the body as the **raw** IPC payload and `{id, method, url, headers}` as percent-encoded JSON in the `x-a0-request` header. Raw bytes avoid JSON number arrays, so 25 MB attachments cross the bridge without blowing up (module docs of `net.rs`).
3. The answer is one byte buffer: a 4-byte big-endian length, the response metadata as JSON (status, status text, headers), then the body. `toResponse()` builds a `Response` from it (no body for 101, 103, 204, 205, 304).
4. An `AbortSignal` calls `net_abort` with the request id; the native task is aborted and the promise rejects with an `AbortError`. Failures without an answer reject with a `TypeError`, like `fetch`.

On the Rust side, `parse_meta()` accepts only `http` and `https` URLs (no `file:`), and the shared `reqwest` client (`http_client()`) keeps no cookies, follows redirects only to http(s), has a 30-second connect timeout but none for the body (large uploads take as long as they take), and sends `User-Agent: action0/<Cargo version>`. Sign-in uses the same client.

## AI assistant

The AI assistant's keys never reach the web view in the apps. `src/platform/native/ai.ts` implements the `AiBackend` (`src/ai/backend.ts`) over the `ai_*` commands; the web app's backend keeps keys in browser storage instead ([ai.md](ai.md)).

- **Keys:** `ai_save_key` keeps the key with the service's API address (`base`, e.g. `https://api.anthropic.com/v1`) and the header it goes in. `ai_request` adds it only to requests whose URL, after parsing, is that address or below it (`base/…`, `base?…`), so `..`, a user name or a look-alike host can't send it elsewhere. A header the UI set for the key itself is dropped. Services without a key (Ollama, LM Studio) are sent as they are; only `http`/`https` URLs are allowed.
- **Streaming:** the answer streams through a `tauri::ipc::Channel`: a JSON `{kind: "head", status, statusText, headers}`, then the body's chunks as raw bytes as they arrive (`response.chunk()`), then `{kind: "end"}`, or `{kind: "error", message}` if the connection breaks off. The command rejects only when there was no answer at all, and `ai_abort` stops the task. `send()` turns this into a `Response` with a streaming body: it resolves on the head, closes the body on the end event (which may arrive after the command settles), and aborts on its `AbortSignal` or when the body is cancelled.
- **OpenRouter:** `ai_openrouter_sign_in` opens `openrouter.ai/auth` with a PKCE challenge and `callback_url=http://localhost:<port>/callback` (the loopback listener), exchanges the code at `/api/v1/auth/keys` for a key billed to the user's credit, and keeps it like any other key (for `https://openrouter.ai/api/v1`). The UI only learns that it worked.
- **Sign in with ChatGPT:** uses the user's ChatGPT plan instead of a key. The first sign-in registers this install: `client_id=dynamic_agent_client`, `agent_name_hint=action0` and `ext_agent_host_id` (a random `urn:uuid:` kept in `ai.vault`); the browser comes back to `http://127.0.0.1:<port>/auth/callback` (ChatGPT refuses `localhost`) with the code and the client id issued to the install, which later sign-ins reuse. The code is redeemed with PKCE and `resource=https://api.openai.com/v1`; the sign-in counts only if `chatgpt.tokens.use.direct` was granted and the ID token's audience and nonce match. The refresh token (30 days, rotating) is kept in `ai.vault`; access tokens (one hour) stay in memory, are renewed one at a time two minutes before they run out, and are only sent to `https://api.openai.com/v1`. A sign-in that can't be renewed is answered as a 401 with `{"error": {"code": "sign_in_again"}}`, so the UI asks to sign in again. Signing out revokes the refresh token.
- **Sign-in errors** are the same `AuthError` kinds as accounts' (`cancelled`, `denied`, `network`, `provider`), as `NativeAuthError`s in the UI. One AI sign-in runs at a time; a new one cancels the one waiting.

## IMAP and SMTP

"Other mail server" accounts exist only in the apps: a browser can't open TCP connections. The native side (`src-tauri/src/imap/`) talks IMAP (`async-imap`) and SMTP itself; the UI's IMAP provider reaches it through `createNativeImapBridge()` in `src/platform/native/imap.ts`. The contract is TypeScript: `src/accounts/mailServer.ts` (adding accounts, errors) and `src/providers/imap/bridge.ts` (mail); the Rust types serialize to exactly those shapes. No mail is written to disk: messages and lists are cached in memory only.

**Accounts.** `imap.vault` (the third vault file, with the same key) keeps, per account `imap:<lower-case address>`: address, name, settings (IMAP and SMTP host, port and security, user name), the password or the Yahoo/AOL client and refresh token, the SHA-256 of a trusted certificate (`pinned`) and the SMTP server's `SIZE` (`maxBytes`). `imap_accounts` lists them without secrets (`MailServerAccountInfo`, with `signIn` `password`, `yahoo` or `aol`); access tokens stay in memory. Secrets are never logged (their `Debug` leaves them out).

**Adding an account** (`imap_connect`): for Yahoo/AOL the browser sign-in comes first; then the IMAP login, then the SMTP login (`EHLO`, `AUTH`, `QUIT`). Only if both work is the account kept (a known one is replaced, its connections closed); the IMAP session goes straight into the account's pool, and the UI gets the `MailServerAccountInfo`. Errors say which server failed (`server: "imap" | "smtp"`).

**TLS and certificates** (`tls.rs`). Always TLS 1.2 or later: from the start (`tls`) or with STARTTLS (`starttls`), which is then required. A server that doesn't offer STARTTLS, or refuses it, fails with `tls`; nothing ever logs in unencrypted. After STARTTLS the capabilities (IMAP) or extensions (SMTP) are asked again, and bytes an SMTP server sends after its `220` are refused as an injection. Certificates are checked like the system checks them (desktop: `rustls-platform-verifier`; Android: Mozilla's roots, as in [Networking](#networking)). A refused certificate fails with `untrusted` and its details (`certificate`: SHA-256, subject, issuer, validity, host names, which server). If the user trusts it, the UI connects again with its fingerprint as `trust`: that one certificate is then accepted for the account whatever its name or issuer (TLS signatures are still checked), and kept as `pinned` if a server needed it. The pin only adds to what the system trusts, like Thunderbird's exceptions: a server that later gets a proper certificate keeps working, and an SMTP server on another host with a valid certificate needs no pin. Any other certificate the system refuses is `untrusted` again (the UI says it changed); nothing is ever trusted without asking. `imap_forget_certificate` drops the pin and the connections that used it.

**Logging in** (`session.rs`): 15 seconds to connect (TCP, then TLS or STARTTLS and the greeting), 60 to log in. A password goes as `AUTHENTICATE PLAIN` (in one step with `SASL-IR`) if the server offers it, else `LOGIN` unless `LOGINDISABLED`; a Yahoo/AOL token as `OAUTHBEARER` if offered, else `XOAUTH2`. Then `CAPABILITY` again, `ID ("name" "action0" "version" "<version>")` where supported, and `ENABLE` for what the server offers of `CONDSTORE`, `QRESYNC` and `UTF8=ACCEPT` (what was turned on is kept with the session). How failures reach the UI:

| What happened                                                                                       | `kind`                          |
| --------------------------------------------------------------------------------------------------- | ------------------------------- |
| `NO` to the login (but `[UNAVAILABLE]`: `server`)                                                   | `auth`: the UI shows Reconnect  |
| No connection, DNS failure, timeout, connection dropped                                             | `unreachable`                   |
| TLS handshake failed, no STARTTLS                                                                   | `tls`                           |
| The certificate isn't trusted (or isn't the pinned one)                                             | `untrusted`, with `certificate` |
| Other `NO`/`BAD` (`message` is the server's text); `[NONEXISTENT]`/`[TRYCREATE]`, `[ALREADYEXISTS]` | `server`; `notFound`, `exists`  |

**Connections** (`pool.rs`): each account has up to two worker sessions (IDLE's comes on top), each handed to one caller at a time and kept afterwards. A session unused for more than four minutes (wall-clock time, so a sleeping computer counts) gets a `NOOP` first; a broken one is replaced by a new connection. A refused login is remembered and answered at once until the account reconnects, so a wrong password isn't retried until the server locks the account. `imap_reconnect` tries the new password (or a new Yahoo/AOL sign-in) on IMAP, keeps it only if that works, and starts the account's connections afresh; `imap_remove` forgets the account, what's kept in memory about its mail, and closes its connections (IDLE's too).

**Sending** (`imap_send`, `smtp.rs`): the message is the raw payload, the envelope `{key, from, to}` the percent-encoded JSON in the `x-a0-imap` header (like `net_fetch`). A small client of our own, because lettre 0.11 builds its rustls config itself and so couldn't check certificates as above: `EHLO`, `STARTTLS` and `EHLO` again where needed, `AUTH PLAIN` (else `LOGIN`) or `OAUTHBEARER` (else `XOAUTH2`), `MAIL FROM` with `SIZE=` (and `BODY=8BITMIME`, `SMTPUTF8` where needed and offered), `RCPT TO` for each address, `DATA` with CRLF line ends and dot-stuffing. A mail bigger than the server's `SIZE` isn't sent at all. Addresses with line breaks, spaces or angle brackets are refused before connecting. Replies: 535 and the like are `auth`, 552 `tooBig`, other 5xx on `MAIL`, `RCPT` or `DATA` `rejected` (`message` is the server's text, with the refused recipient), 4xx (try later) `server`.

**Yahoo and AOL** (`oauth.rs`): the browser with PKCE (S256) and `state` at `api.login.yahoo.com` / `api.login.aol.com` (`/oauth2/request_auth`, tokens from `/oauth2/get_token`), scope `mail-w`, coming back to `http://127.0.0.1:<port>/` (the loopback listener of [Native sign-in](#native-sign-in); Android: see [android.md](android.md)). The UI sends the app's registration (client ID, and the secret only if it has one) in `setup.credentials`. Refresh tokens rotate and are kept in the vault; access tokens stay in memory and are renewed one at a time. A token the server refuses is renewed once; a refused renewal is `auth` (Reconnect), a failed sign-in `oauth`.

**Finding settings** (`imap_discover`, `discover.rs`), like Thunderbird:

1. Gmail addresses (`gmail.com`, `googlemail.com`) get `better: "gmail"` with Gmail's IMAP settings (for those who use IMAP anyway) and the app-password page; Outlook.com's (`outlook.*`, `hotmail.*`, `live.*`, `msn.com`) `better: "microsoft"`.
2. The provider's own configuration: `https://autoconfig.<domain>/mail/config-v1.1.xml?emailaddress=<address>` and `https://<domain>/.well-known/autoconfig/mail/config-v1.1.xml`.
3. Mozilla's ISPDB: `https://autoconfig.thunderbird.net/v1.1/<domain>` (it learns only the domain).
4. MX (desktop only: Android doesn't let apps read the DNS settings): mail servers at Google give `better: "gmail"`, at `*.mail.protection.outlook.com` `better: "microsoft"`; otherwise the MX host's registered domain (`mx01.emig.gmx.net` → `gmx.net`, a guess without the public suffix list) is looked up in the ISPDB, then its own autoconfig (without the address).
5. Nothing: `source: "none"`, and the settings are typed in.

Steps 2 to 4 run at the same time (5 seconds each, https only, also after redirects) and the first in that order that found settings wins. From a configuration file (`clientConfig/emailProvider`) come `displayName` and the first IMAP and SMTP servers with `SSL` or `STARTTLS` (never plain), those with a password login preferred, `%EMAILADDRESS%`, `%EMAILLOCALPART%` and `%EMAILDOMAIN%` filled in. A small table adds what's known about some providers (by the address's domain, else the IMAP server's): Yahoo and AOL (`oauth` and the app-password page), iCloud and Fastmail (app-password pages), GMX and web.de (where IMAP is switched on first).

**Mail** (`imap_call`, `imap_bytes`, `imap_append`; `calls.rs`). Each operation runs on a pooled session of the account; those that may run twice run with `Imap::run` (once more on a new connection if a kept one broke), APPEND doesn't (a kept session gets a `NOOP` first instead). What's kept in memory per account while the app runs (`state.rs`): where each message is, the folders as last listed, the lists being paged through, the last 20 messages opened (50 MB at most), what the last change check saw, and where conversations were listed. async-imap's own commands drop much of what's needed (EMAILID, THREADID, X-GM-THRID, APPENDUID, COPYUID), so `proto.rs` sends commands itself and reads imap-proto's parse of each answer. An answer imap-proto can't parse leaves the connection unusable: the session is replaced, and a list or change check is fetched again without `BODYSTRUCTURE` (the likeliest cause).

**Ids** (`ids.rs`). Folders are `f:<path>` (the path decoded from modified UTF-7 unless `UTF8=ACCEPT` is on; commands use the name as the server listed it), views `v:flagged` and `v:all`. A message keeps its id when it moves: `e:<EMAILID>` where the server has `OBJECTID` (RFC 8474), `g:<X-GM-MSGID>` on Gmail, else `l:f:<path>:<UIDVALIDITY>:<UID>` from where action0 first saw it. The id map (in memory, 50,000 messages per account) knows where each message is now: filled by every list and fetch, moved along by `COPYUID` and `APPENDUID` (UIDPLUS) or, without them, by searching the target for the Message-ID. An `l:` id the map doesn't know (after a restart) is looked for where its text says; `e:`/`g:` ids by `UID SEARCH EMAILID` folder by folder (Gmail: `X-GM-MSGID` in All Mail).

**Folders** (`folders.rs`): `LIST "" "*" RETURN (SPECIAL-USE STATUS (MESSAGES UNSEEN))` where the server has LIST-EXTENDED, LIST-STATUS and SPECIAL-USE, else `LIST` and `STATUS` per folder (sent 50 at a time). Roles come from special use (`\Sent \Drafts \Trash \Junk \Archive \All \Flagged`), else from the name, ignoring case, at the top level or right under INBOX: Sent, Sent Items, Sent Messages, Sent Mail, Gesendet, Gesendete Objekte/Elemente; Drafts, Entwürfe; Trash, Deleted Items/Messages, Papierkorb, Gelöschte Elemente/Objekte; Junk, Spam, Junk E-mail, Junk-E-Mail; Archive, Archives, Archiv. One folder per role. `\Noselect` and `\NonExistent` folders aren't selectable; parents LIST doesn't name are added that way. Where every folder lives below `INBOX.` and role folders are there (Courier, Cyrus), they show at the top level and new folders go there too. Sent, Drafts and the server's own \All and \Flagged folders take no moved mail. The views follow unless the server has its own \Flagged or \All folder (Gmail), which then plays the role: Flagged, and the hidden All mail ("Everywhere"), both over every folder but Trash, Junk and the server's \All/\Flagged.

**Lists** (`list.rs`, `search.rs`). The first page takes a snapshot of the matching UIDs in order: `UID SORT (REVERSE ARRIVAL)` (or `ARRIVAL` for oldest first) where the server has SORT, else `UID SEARCH` in UID order; always `UNDELETED`. Pages are slices of it, and the cursor is `<snapshot>:<offset>`; a snapshot that's gone (a restart, or 20 lists since) is taken again and the page starts at the same offset. Views search each folder (the newest 2,000 matches each), fetch their INTERNALDATEs and merge. A page's rows are one `UID FETCH` (flags, INTERNALDATE, BODYSTRUCTURE, the address, subject and threading header fields read with mail-parser, and EMAILID/THREADID or X-GM-MSGID/X-GM-THRID). Snippets: the server's `PREVIEW` (RFC 8970) where it has it, else the first 2 KB of the first text/plain part (else text/html, tags removed), decoded with its charset and transfer encoding. `hasAttachments`: a part marked as attachment, an attached message, or a part with a file name that isn't an inline image. Search turns `from:`, `to:`, `subject:`, `is:unread`, `is:read`, `is:starred`/`is:flagged`, quoted phrases and words (`TEXT`) into search keys that must all match; non-ASCII goes as UTF-8 (quoted after `ENABLE UTF8=ACCEPT`, else as literals with `CHARSET UTF-8`). Gmail gets the whole text as `X-GM-RAW`.

**Conversations** (`threads.rs`). A message's thread key is the server's thread id (`t:<THREADID>`, `g:<X-GM-THRID>`), else the first Message-ID of its References, else In-Reply-To, else its own Message-ID (`m:<id>` without any). `threads` pages through the same snapshots and groups each page's rows; a conversation shows on the page of its newest message, and its older messages further down are left out of later pages. `thread` searches the Inbox, Sent, Archive and the folder the conversation was listed in (`THREADID`, `X-GM-THRID`, or the Message-ID in the Message-ID, References and In-Reply-To headers), reads the newest 100 per folder whole and returns them oldest first; a message in two folders under one id (Gmail's labels) counts once, a Sent copy and its Inbox delivery (mail to yourself) both count.

**Messages** (`read.rs`, `parse.rs`): `message` fetches `BODY.PEEK[]` and parses it with mail-parser into `ImapMessage`: HTML and text bodies as they are, attachments (and inline parts with a Content-ID) by their MIME part path ("2", "1.3"), `List-Unsubscribe(-Post)`, the first `text/calendar` part, `draft` from `\Draft`. `imap_bytes` gives the whole message or one part decoded (an attached message as .eml), from the in-memory cache when the message was just opened.

**Changes** (`write.rs`): `flags` is `UID STORE ±FLAGS.SILENT`; `move` is `UID MOVE`, else `UID COPY`, `\Deleted` and an expunge. Expunging takes only the messages meant: `UID EXPUNGE` with UIDPLUS; without it a plain `EXPUNGE` would also take messages another program marked `\Deleted`, so it's only sent when no others are marked, and otherwise the messages stay marked (lists leave them out) until the folder is expunged. `delete` marks and expunges; `empty` deletes all of a folder's mail; `markAllRead` stores `\Seen` on the unread ones (per folder in the views) and returns their ids. `createFolder` uses `CREATE … (USE (\Archive))` where the server has CREATE-SPECIAL-USE (a plain CREATE if it refuses) and subscribes; `updateFolder` renames (subfolders move along); `deleteFolder` renames the folder into Trash (creating Trash if there's none), or deletes it with its subfolders when it's in Trash already. `imap_append` stores with the flags and the current date and finds the new message's id from APPENDUID, else by its Message-ID.

**New mail** (`sync.rs`). The `changes` token is base64 JSON of every folder's UIDVALIDITY, UIDNEXT, HIGHESTMODSEQ, MESSAGES and UNSEEN; no token gives just the token. A check asks STATUS for all folders (with LIST-STATUS in the LIST) and looks into those that changed: new UIDs since the old UIDNEXT are `added`; with QRESYNC, `UID FETCH 1:<old UIDNEXT-1> (FLAGS) (CHANGEDSINCE <modseq> VANISHED)` gives flag changes (`updated`) and expunged UIDs (`removed`); with CONDSTORE only, CHANGEDSINCE gives the flag changes and expunges are found by comparing the newest 200 UIDs with the last check; without either, the newest 200 UIDs and flags are compared (the Inbox's at every check, so its flags are followed even when its counts don't change). A message removed in one folder and added in another under the same id moved: it comes as `updated` with its new folder. A changed UIDVALIDITY, folders that came (with mail) or went, more than 200 changes, an unreadable token, or changes that can't be told apart (no memory of a folder yet) give `reset: true`.

**IDLE** (`idle.rs`, desktop): one more session per account, opened at start and again after `imap_connect`, `imap_reconnect` and `imap_forget_certificate`, and closed by `imap_remove`. It IDLEs on the Inbox and emits `imap-changed` (`{key}`) a second after the last of a burst of EXISTS, EXPUNGE or FETCH answers; `desktop.ts` relays it to the UI's "check for mail now". IDLE is renewed every 25 minutes; after an error the session is opened again after 30 s, 1 minute, then every 5 minutes. Servers without IDLE get none; a refused login stops it until the account reconnects. Android has no IDLE: its background check covers IMAP (see [android.md](android.md#the-background-check)).

**Filters** (`sieve_*`, `sieve.rs`): a small ManageSieve client (RFC 5804) built like the SMTP one. It connects to port 4190 and requires STARTTLS (data before TLS is refused; the capabilities are read again after it), checks the certificate like IMAP (the account's pin included), logs in with the mail login (`AUTHENTICATE "PLAIN"`, or `OAUTHBEARER`/`XOAUTH2` with one token renewal on refusal) and speaks `LISTSCRIPTS`, `GETSCRIPT`, `PUTSCRIPT` (a `{n+}` literal), `SETACTIVE` and `LOGOUT`. The filter server is kept in the account's vault entry (`ImapAccount.sieve`: host, port, extensions, whether the user chose it). Finding one tries a small table first (mailbox.org, Posteo; Gmail, Outlook, Yahoo, AOL, iCloud, GMX, WEB.DE, Fastmail and Zoho answer `notFound` at once), then the IMAP host on 4190. `sieve_write` reads the active script and writes only if it is still `expected` (line endings aside), else `changed`; a refused script is `rejected` with the server's text. Scripts are capped at 4 MB. The Sieve itself is read and written in TypeScript ([providers.md](providers.md#sieve-mail-servers)).

**Tests.** `imap/testing.rs` has a scripted server (`S:` lines it sends, `C:` lines the client must send, over `tokio::io::duplex` or a socket; `logged_in()` starts after the login) and certificates made with `rcgen` (a test CA stands in for the system's roots). The login, STARTTLS, the error mapping, the pool, SMTP and the pinned certificate are tested against it, discovery against `wiremock`; so are the mail operations: LIST with special uses and German names, `INBOX.` and Gmail's folders, modified UTF-7, list pages (rows, snippets, PREVIEW, snapshots), views, search keys, conversations across pages, MOVE with COPYUID, COPY without UIDPLUS, delete and expunge, APPEND with APPENDUID, folder management, the change token (QRESYNC with VANISHED, comparing without CONDSTORE, a changed UIDVALIDITY), IDLE, and the commands' JSON; mail-parser's mapping with real-looking messages. `imap/live.rs` has `#[ignore]`d tests against a real server (e.g. Dovecot in Docker), including the mail operations in a folder of their own and IDLE: `ACTION0_IMAP_TEST=1` with `ACTION0_IMAP_HOST`, `_PORT`, `_SECURITY`, `_USER`, `_PASSWORD` (and `ACTION0_SMTP_HOST`, `_PORT`, `_SECURITY`, `ACTION0_SMTP_TO`), run with `cargo test --locked -- --ignored live`. A self-signed certificate is trusted the way the UI does it.

## CalDAV

Calendar servers are the calendar counterpart of IMAP: `src-tauri/src/caldav/` finds them, walks to the calendar home with the login, keeps the login in `caldav.vault` (the mail account's, or a separate one) and carries the provider's DAV requests, adding the login only for the server's own hosts and applying its pinned certificate. The DAV and iCalendar work happens in the TypeScript provider. Details in [caldav.md](caldav.md).

## Tray, close to tray and autostart

All in `src-tauri/src/shell.rs`:

- **Tray icon** (the window icon) with the tooltip "action0" and a menu: **Show action0**, **New mail** (an empty `a0://compose`) and **Quit**. A left click shows the window where the system reports tray clicks; it doesn't open the menu (`show_menu_on_left_click(false)`). The menu starts in English; `shell_configure` replaces the texts with the interface's (`t.desktop.tray`).
- **Close to tray:** `on_window_event` turns a close request into hiding the window and emits `a0://closed-to-tray`. The UI then shows a notification once ("still running in the tray"; remembered as `a0.settings.trayNoticeShown` in localStorage). Settings → App can switch this off (`closeToTray`, on by default), and closing then quits. **Quit** in the tray and <kbd>Ctrl</kbd>/<kbd>⌘</kbd>+<kbd>Q</kbd> always quit.
- **macOS:** clicking the dock icon of a hidden app shows it again (`RunEvent::Reopen`).
- **Checking mail while hidden:** hidden web views may throttle their own timers, so a native task emits `a0://poll` every 5 minutes while the window is hidden, and `useMailSync()` checks all accounts.
- **Window state:** `tauri-plugin-window-state` restores size, position, maximized and fullscreen state, but not visibility, which stays the native side's call.
- **Autostart** (`tauri-plugin-autostart`, a LaunchAgent on macOS) is off by default and toggled in Settings → App (`src/ui/settings/DesktopSettings.tsx`). The system starts the app with `--hidden` (`HIDDEN_ARG`); `lib.rs` sees the argument and `shell::setup` then leaves the window hidden, so the app starts in the tray.

## Single instance, mailto and deep links

`tauri-plugin-single-instance` is the first plugin registered, so a second start reaches the running app before anything else. With its `deep-link` feature it first hands the second start's arguments to the deep-link plugin; then `on_second_instance` shows the window.

How `mailto:` links arrive differs per system:

| System       | First start                                        | While running                                                          |
| ------------ | -------------------------------------------------- | ---------------------------------------------------------------------- |
| Linux, macOS | `deep_link().get_current()`                        | `deep_link().on_open_url` (via the single-instance hand-over on Linux) |
| Windows      | `mailto:` arguments of the process (`mailto_args`) | `mailto:` arguments of the second start, in `on_second_instance`       |

On Windows, `src-tauri/tauri.windows.conf.json` clears the deep-link schemes and the installer registers action0 as a mail client instead ([hooks.nsh](building-and-deploying.md#windows-installer-hooks)), which passes the link as `"%1"`.

**The `ui_ready` flag.** A link can arrive before the UI exists. `compose()` shows the window and then either emits `a0://compose` (UI ready) or queues the link in `pending`. At startup the UI calls `shell_take_compose`, which returns the queue and sets `ui_ready`, so every later link comes as an event. On the TS side `startDesktop()` keeps links (queued ones and events) in `waiting` until the first `onCompose` listener subscribes (`DesktopIntegration`), which hands them to `composeFrom()` in `src/ui/composer/useComposeActions.ts`: a new mail with the link's fields, from the account last sent from (`lastSendAccount`).

**Making action0 the default mail app** (Settings → App, `shell_default_mail_app`):

- Linux: `deep_link().register("mailto")` writes a handler `.desktop` file into the user's applications folder and makes it the `x-scheme-handler/mailto` default with `xdg-mime` (needs `xdg-mime` and `update-desktop-database`). Result `done`.
- Windows: opens `ms-settings:defaultapps`, where the user chooses action0. Result `settings`.
- macOS: the user chooses it in Mail's settings. Result `manual`.

`mailto:` links inside the app and inside mail open a new mail too, through `followLink` (see [below](#the-platform-interface)).

## Notifications and the unread badge

**Notifications** go through `tauri-plugin-notification` (`notifications` in `src/platform/native/desktop.ts`): `supported` is always true and `mustAsk` false (the system decides, no browser prompt); the permission state is read at start and after `request()`. `show()` sends a notification with a numeric id and remembers its click handler (the last 50); `onAction` brings the window forward (`unminimize`, `show`, `setFocus`) and runs the handler. The callers are the same as in the web app: new Inbox mail (`src/ui/sync/notifications.ts`), event reminders (`src/ui/reminders/Reminders.tsx`) and the one-time tray notice.

**The unread count** comes from `useDocumentTitle()` (`src/ui/sync/useDocumentTitle.ts`), which also sets the document title (the tab title in the web app). It calls `platform.setUnreadCount(count, label)`, which skips unchanged values and invokes `shell_set_unread`:

- `window.set_badge_count`: the dock or launcher badge where the system has one (cleared at 0).
- Windows: a taskbar overlay icon, a 32 × 32 PNG the UI draws on a canvas (a red circle with the count, "99+" above 99).
- The tray: the tooltip is the label everywhere; on Linux and macOS the count also shows next to the icon (`set_title`).

## Spell checking

The editors set `spellcheck` from Settings → Writing (`RichTextEditor`, the subject, the event title); each web view checks with its own engine:

- **Linux.** WebKitGTK checks only when the app turns it on, in the languages it's given, through Enchant and the system's hunspell dictionaries. `spelling_dictionaries` looks where Enchant's hunspell provider looks (`~/.config/enchant/hunspell`, then `hunspell/` in each of `XDG_DATA_DIRS`) and lists `xx_YY.dic` files with their `.aff`. `spelling_set_languages` sets them on the web view's `WebContext` (through `with_webview`) and reads back the ones that loaded. The UI picks the languages (`applySpelling()` in `src/ui/settings/spelling.ts`): the ones ticked in Settings that are installed, else the browser's languages and the interface's, matched to the installed dictionaries (`de` → `de-DE`, `en` → `en-US`). `DesktopIntegration` applies them at start and on every change; Settings lists the dictionaries afresh each time it opens and says when none loaded. WebKitGTK's own context menu offers the suggestions, "Ignore Spelling" and "Learn Spelling" (Enchant's personal word list).
- **macOS.** WebKit checks while typing only if the app's defaults say `WebContinuousSpellCheckingEnabled`; `check_while_typing()` sets it before the window exists. macOS detects the language.
- **Windows.** WebView2 checks in the display language, which wry sets; it has no way to set spelling languages.
- **AppImage.** It bundles WebKitGTK and Enchant, but Enchant loads its provider from the path it was built with (Ubuntu's), so outside Debian and Ubuntu it may find no dictionaries; Settings then says so. The .deb and .rpm use the system's libraries.

## Updater

`tauri-plugin-updater` with the endpoint and public key in `plugins.updater` of `src-tauri/tauri.conf.json`. The UI checks at start and daily, shows a bar and installs only on a click, then relaunches (`plugin-process`). The details, the signing keys and `latest.json` are in [releasing.md](releasing.md#latestjson-and-how-installed-apps-update).

## The Platform interface

Everything that differs between browser and app sits behind one interface, `Platform` in `src/platform/types.ts`:

| Member                 | Web (`src/platform/web.ts`)                                           | Desktop (`src/platform/native/desktop.ts`)                                                             |
| ---------------------- | --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `kind`                 | `"web"`                                                               | `"desktop"`                                                                                            |
| `openExternal(url)`    | New tab (`noopener,noreferrer`)                                       | Default browser (`openUrl`)                                                                            |
| `followLink(href)`     | `false`: links open as they do                                        | Same origin: `false`; `http(s):` → default browser; `mailto:` → new mail; anything else isn't followed |
| `saveFile(blob, name)` | Download as `application/octet-stream`                                | Save dialog, then `writeFile`                                                                          |
| `openFileLater()`      | Opens a tab inside the click, fills it with a blob of the forced type | `shell_open_file` (the system's PDF viewer)                                                            |
| `notifications`        | The browser's `Notification` (not on touch devices)                   | `plugin-notification`                                                                                  |
| `setUnreadCount`       | Nothing (the tab title shows it)                                      | `shell_set_unread`                                                                                     |
| `onPollRequest`        | Never fires                                                           | `a0://poll`                                                                                            |
| `onCompose`            | Never fires                                                           | `a0://compose` and links from startup                                                                  |
| `desktop`              | Absent                                                                | `DesktopControls`: version, OS, close-to-tray, autostart, default mail app, updates, quit              |
| `spelling`             | Absent (the browser's languages)                                      | Linux only: `spelling_dictionaries`, `spelling_set_languages`                                          |

- `src/platform/context.ts` provides it as a React context (`PlatformContext`, default `webPlatform`); components use `usePlatform()`. `AppProviders` sets the value from the services.
- The desktop platform also registers a capturing `click` listener on the document, so links of the app itself (with `target="_blank"`, which would open nothing in a web view) go through `followLink` too. Links inside mail are handled by the mail frame (`followLinkClick()` in `src/ui/reader/links.ts`).
- `DesktopIntegration` (`src/ui/desktop/DesktopIntegration.tsx`) is the UI's desktop glue: it pushes the close-to-tray setting and tray texts, subscribes to `onCompose`, shows the tray notice, sets the spelling languages (Linux), registers <kbd>Ctrl</kbd>/<kbd>⌘</kbd>+<kbd>Q</kbd> and renders the update bar. It renders nothing in the web app.
- ESLint enforces the boundary (`no-restricted-imports` in `eslint.config.js`): `@tauri-apps/*` is forbidden in `src/` outside `src/platform/native/`. Two exceptions in the config: tests may import anything, and `src/core` has its own import rule, which doesn't list Tauri. Tests use a fake desktop platform (`src/test/desktopPlatform.ts`) instead of Tauri ([testing.md](testing.md)).
